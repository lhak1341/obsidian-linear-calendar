# No shared CalendarWidget factory between RollingStrip and LinearCalendarView

`RollingStrip` (behind the public `mountRollingStrip`; it replaced `mountMonthStrip` in 68da6f5) and `LinearCalendarView` both call `new CalendarRenderer(...)`, which looks like shared setup logic worth extracting. We decided not to introduce a `createCalendarWidget()` factory because the two callers need meaningfully different resize policies: `RollingStrip` re-renders from a `ResizeObserver` guarded on actual width change (`w !== lastWidth && w > 0`) to avoid false triggers in the dashboard container; `LinearCalendarView` has no resize handling at all, since its CSS grid `1fr` columns adapt natively (a `ResizeObserver` there rebuilt every day cell on each pane resize). A factory that encapsulates both would need to parameterize resize behavior, making it more complex than just calling `new CalendarRenderer()` directly. The deletion test confirms it: remove the factory and both callers simply construct `CalendarRenderer` themselves — no complexity concentrates behind the seam. The `CalendarRenderer` constructor is the right level of abstraction here.

Sharing the note-mutating callbacks (drag-commit, reminder promotion, edit) between the two callers is a separate matter and is done in `view/calendarInteractions.ts`. Callback wiring may be shared; widget construction and resize policy may not.

## Addendum: subscriptions, category filter and interactions move into CalendarRenderer

`CalendarRenderer` now subscribes to items, daily notes and settings itself (`subscribeRepaints`, `view/calendarRepaints.ts`), owns the category toggle, and calls `createInteractions` from the shared `CalendarDeps`. A host supplies a `CalendarHost`: its container, a `config()` getter read on every full render, its `hiddenCategories` set, an `afterRender` hook and its own day callbacks. This is callback wiring in this ADR's sense: each host still constructs its own `CalendarRenderer` and keeps its own resize policy, so the decision above stands.
